Introduction to Git

Installation, Basic Commands

git
GitHub

Installation and Configuration

Installation

  • macOS: Install Xcode Command Line Tools. Open Terminal and run:
xcode-select --install
  • Linux: Git may already be installed. If not, install it using:
sudo apt install git
  • Windows: Download Git for Windows from
    https://git-scm.com/download/win and install it with default settings.

To verify that Git is installed, run:

git --version

Sign Up for GitHub

Follow these steps to create a GitHub account:

  1. Open the GitHub website:
    https://github.com/

  1. Click Sign up in the top-right corner.

  2. Enter your:

    • Email address
    • Password
    • Username

  1. Choose your email verification preferences.

  2. Complete the verification challenge.

  3. Click Create account.

  4. GitHub will send a verification code to your email. Enter the code to activate your account.

  5. Choose the Free plan (sufficient for this course).

After this, your GitHub account is fully ready.

Git Configuration

Check Current Git Config

Run the following command to see your current configuration (should be mostly empty on new installations):

git config --global --list

Set Username

git config --global user.name "your_name"

Set Email

git config --global user.email "your_email"

Verify Updated Config

Check again:

git config --global --list

Generate Personal Access Token (PAT)

GitHub no longer accepts passwords for Git operations.
You must generate a Personal Access Token (PAT).

Steps

  1. Sign in to your GitHub account.

  2. Navigate to:
    Profile → Settings → Developer settings → Personal access tokens → Tokens (classic)

  1. Click Generate new token.

  2. Select scopes (minimum recommended):

    • repo
    • read:org
    • workflow
    • or simply select all
  1. Set No expiration.

  1. Click Generate token.

  2. Copy the token and store it securely.

You will paste this token when executing:

git push

Generate SSH Key (Optional but Recommended)

SSH keys allow secure password-less authentication with GitHub.

Steps

  1. Open Terminal or PowerShell.

  2. Generate a new SSH key:

ssh-keygen -t rsa -b 4096 -C "your_email@example.com"
  1. When prompted for a location, press ENTER to use the default:
~/.ssh/id_rsa
  1. When asked for a passphrase:
    • leave empty for no passphrase
    • or enter a secure passphrase
  2. Display your public key:
cat ~/.ssh/id_rsa.pub

Copy SSH Key

macOS:

pbcopy < ~/.ssh/id_rsa.pub

Windows PowerShell:

Get-Content ~/.ssh/id_rsa.pub | Set-Clipboard

Add SSH Key to GitHub

  1. Go to GitHub → Settings → SSH and GPG keys
  2. Click New SSH key
  3. Paste your key
  4. Save

Create a Remote Repository on GitHub

  1. Log in to your GitHub account.
  2. Click the New repository button.
  3. Fill in:
    • Repository name
    • Description (optional)
    • Set it to Public
  4. Do NOT initialize with README (we will create files locally).
  5. Click Create repository.

GitHub will show you the remote URL, e.g.:

https://github.com/username/myrepo.git
  1. Choose a folder on your computer.
  2. Initialize Git in that folder:
git init
  1. Connect your local repo to the remote repo:
git remote add origin https://github.com/username/myrepo.git
  1. Verify remote:
git remote -v

Adding a Dummy File

Inside your local project folder, create a simple file:

echo "This is a test file" > test.txt

Then stage it:

git add test.txt

Commit it:

git commit -m "Add test file"

Pushing to GitHub

Push your commit to GitHub:

git push -u origin main

If your default branch is master, use:

git push -u origin master

You will be asked for:

  • username
  • Personal Access Token (instead of password)

After authentication, your file will appear on GitHub.

Pulling Changes from GitHub

If changes have been made remotely, you can update your local repo:

git pull origin main

or:

git pull

Use pull whenever you want your local files to match GitHub.

Cloning a Repository (Alternative Workflow)

Instead of creating a folder manually, you can clone an existing remote repo:

git clone https://github.com/username/myrepo.git

This will:

  • Create the folder
  • Download all existing files
  • Set the remote origin automatically

Summary Workflow

  1. Create repo on GitHub (empty, no README)
  2. git init locally
  3. Create files
  4. git add
  5. git commit
  6. git remote add origin <url>
  7. git push

or use:

  • git clone → edit → git add → git commit → git push

Homework

This task ensures that you can create repositories, work locally, work remotely, and synchronize changes between GitHub and your machine.

Follow the steps below exactly in order.

Create a Remote Repository on GitHub

  1. Log in to your GitHub account.
  2. Click New Repository.
  3. Set:
    • Repository name: `choose any name
    • Visibility: Public
  4. Do NOT initialize with README.
  5. Click Create Repository.

Copy your remote URL, e.g.:

https://github.com/yourusername/myrepo.git

Clone the Repository to Your Computer

In a folder of your choice, open Terminal or PowerShell and run:

git clone https://github.com/yourusername/myrepo.git

This will create a new local folder with the repository inside.

Create a Dummy File Locally

Navigate into the cloned folder:

cd myrepo

Create a simple text file:

echo "This is my first Git test file." > test.txt

Stage and commit the file:

git add test.txt
git commit -m "Add test file"

Push it to GitHub:

git push

Check GitHub — you should now see test.txt in the repository.

Add a New File on GitHub (Remote)

  1. Open your repo on GitHub.
  2. Click Add file → Create new file.
  3. Name it: remote_file.txt
  4. Add any text inside it.
  5. Commit the new file.

Pull the New File to Your Computer

Return to your local repo folder and run:

git pull #given the strategy either --rebase or merge

Branching for Product Development

Use Git to develop a data product in small, reviewable changes. The same workflow works when you are learning independently or collaborating with others.

Keep the Branch Structure Simple

  • main contains the stable, working version of the application.
  • Create a short-lived feature branch for a specific improvement.
  • Merge the change after checking that it works, then start the next feature from the updated main.

The examples below use main. If your repository uses master, substitute that name in the commands.

Organize Branches Around Changes

A branch describes a change rather than a permanent developer role. For example:

  • feature/carousel-schema
  • feature/carousel-api
  • feature/analytics-page
  • feature/bandit-evaluation

The database, backend, frontend, and analytical logic still depend on one another. Plan their interfaces and implement them in useful increments; they do not need separate permanent branches.

Example Branch Flow

Step-by-Step Feature Workflow

1. Open the Repository

If you have not cloned it yet:

git clone https://github.com/your-username/your-repo.git
cd your-repo

Otherwise, open your existing local repository.

2. Update the Stable Branch

git checkout main
git pull --ff-only origin main

3. Create a Feature Branch

git checkout -b feature/analytics-page

4. Implement and Check the Change

Make a focused improvement, such as adding a chart to the analytics page. Run the relevant part of the application and check the result against the intended user behavior.

Review the files before committing:

git status
git diff

5. Commit and Push

Stage the files you changed. For example, if you updated the analytics page:

git add app/front/pages/Analytics.py
git commit -m "Add carousel performance chart"
git push -u origin feature/analytics-page

6. Review and Merge

A Pull Request (PR) on GitHub lets you inspect the difference between the feature branch and main, describe the change, and keep a record of the review.

When working independently, you can review and merge your own PR after checking the behavior. When collaborating, a PR also provides a place to ask for feedback.

Pull Requests

Why Pull Requests Matter

Pull Requests help you:

  • review the changes before merging,
  • explain what changed and why,
  • record how you checked the result,
  • discuss implementation choices when feedback is useful,
  • keep main working.

Pull Request Steps on GitHub

After pushing your feature branch:

  1. Open the repository on GitHub.
  2. Click Compare & pull request.
  3. Set base to main and compare to your feature branch.
  4. Add a clear title and describe the product behavior that changed.
  5. Include how you checked it and any known limitations.
  6. Review the diff and address any feedback.
  7. Merge when the change is ready.

For example: feature/analytics-page → main.

Continue from the Updated Version

After the PR is merged:

git checkout main
git pull --ff-only origin main

Create a new feature branch from this version for the next improvement.

Merge Conflicts

A merge conflict happens when Git cannot automatically combine changes from two branches.

Important

This usually happens when:

  • two people edit the same file
  • two people edit the same lines in a file
  • one person deletes something that another person modified

Example Conflict Situation

Suppose:

  • One feature branch changes bandit_utils.py
  • Another feature branch changes the same part of bandit_utils.py

When one branch is merged first, the second branch may conflict.

What a conflict looks like

Git may mark the file like this:

<<<<<<< HEAD
return {"message": "First implementation"}
=======
return {"message": "Alternative implementation"}
>>>>>>> feature-branch

This means Git needs a human to decide which version to keep.

How to resolve a merge conflict

  1. Pull the latest changes from the target branch.
  2. Open the conflicted file.
  3. Find the conflict markers:
    • <<<<<<<
    • =======
    • >>>>>>>
  4. Decide which code should remain.
  5. Remove the conflict markers.
  6. Save the file.
  7. Stage and commit the resolved version.

Example:

git add .
git commit -m "Resolve merge conflict"
git push

Best ways to avoid conflicts

To reduce merge conflicts:

  • pull frequently
  • keep branches focused and small
  • do not let branches drift for too long
  • communicate who is editing which files
  • use Pull Requests early
  • avoid editing the same file in parallel unless necessary

Recommended Development Process

  1. Choose a small improvement linked to the user’s needs.
  2. Update main and create a feature branch.
  3. Implement the change locally.
  4. Check the behavior and review the diff.
  5. Commit, push, and open a Pull Request.
  6. Review and merge the working change.
  7. Pull the updated main before starting the next improvement.
